# 주제 이슈와 검증 위임

OZ = 사용자, GitHub 계정 OruteZ. 보드: https://github.com/users/OruteZ/projects/5

> 사용자 결정 2026-11-08: "이슈가 너무 작은 단위의 일들을 담고 있어서, 전체적으로 어떤 태스크들이 흐름으로 돌아가는지 추적되지 않고 휩쓸리는 느낌이야. status에 "샤용자 대기"를 달고 담당자 라벨을 때는 쪽이 ㅎ훨씬 좋을 것 같아. 또한 각각의 이슈가 훨씬더 큰 작업의 단위를 가지면 좋겠어. 핵심 주제를 중심으로 어떻게 돌아가는지 일렬로 보이도록"

## 1. 구조

이슈 하나 = 큰 **주제** 하나(라벨 `주제`). 기능·화면·도구처럼 여러 번의 기획·구현·확인을 거치는 흐름이다 (예: "장 선택 화면", "다국어", "작업 보드"). 하위 이슈·담당·종류 칸은 없다.

```markdown
## 목표
장 선택 화면을 원정 지도 위 3 레이어로 만든다.

## 요청
> (사용자 원문 인용. 채팅으로 맡긴 일이면 에이전트가, 작업 중에 더 온 요청도 받는 즉시 여기 더한다)

## 흐름
- [x] 기획: docs/ui/stage-select.md (a1b2c3d)
- [x] 구현: L1·L2·L3 (d4e5f6a)
- [x] 사용자: 움직임·그늘 확인 → 3·6 이 어색함
- [x] 구현: 칸 감속 (1cdf593)
- [ ] 사용자: 다시 확인 (아래 확인)
- [ ] 구현: 원정 지도 소품

## 확인
(사용자 대기일 때만. 항목마다 할 일·기대 결과·`- [ ]`)

## 관련
- 안내서: docs/areas/<분야>.md
- 기획: docs/design/<파일>
- 브랜치: [claude/stage-select-1a2b3c](https://github.com/OruteZ/Project-Vampire-Turn-Strategy/tree/claude/stage-select-1a2b3c) (2026-11-08)
```

- `## 흐름` 한 줄 = 한 단계, 앞에 `기획:` `구현:` `사용자:`. 사용자 몫(확인, 결정, docs/design 쓰기, 내려받기·로그인 같은 준비, 허락)은 `사용자:` 단계다. 단계가 일렬로 보이는 것이 핵심이다. 확인에서 나온 고칠 것도 새 이슈가 아니라 다음 단계다
- 요청: 사용자 원문을 `## 요청` 에 인용하고 원하는 것 한 줄마다 단계 하나 이상. 작업 중에 온 요청·질문도 받는 즉시 인용·단계를 더한다
- OZ 가 쓴 `목표`·`요청` 문장은 고치지 않는다. `흐름`·`확인`·`관련` 은 에이전트가 고친다. 세부 기록(무엇을 어떻게 확인했나, 스크린샷 경로)은 댓글에
- 주제 하나 = 세션 하나가 처음부터 닫을 때까지 맡는 분량이다. `사용자:` 단계를 기다린 뒤에도 같은 세션에서 이어 간다. 너무 커지면 사용자에게 나눌지 묻는다
- 새 일은 맞는 주제의 흐름에 더한다. 어느 주제에도 안 맞으면 새 주제를 연다(한두 단계로 끝날 일이면 가장 가까운 주제에)

## 2. 상태와 명령 (GitHub Project "Vampire Spawn 작업" 의 Status)

| 상태 | 뜻 | 누가 바꾸나 |
|---|---|---|
| 미작업 | 열렸지만 아직 아무도 손대지 않음 | 연 때 |
| 작업 중 | 에이전트가 다음 단계를 하고 있음 | 에이전트, 시작할 때 |
| 사용자 대기 | 다음 단계가 `사용자:` 단계. 무엇을 해 달라는지는 `## 확인` 이나 댓글에 | 에이전트, 사용자 단계에 이르렀을 때 (채팅에만 쓰지 않는다) |
| 작업 완료 | 이슈를 닫음 | 닫으면 저절로 (Project 자동화, sync) |

```bash
node tools/board/board.mjs open "<제목>" ["<목표>"]       # 주제 이슈 열기 (라벨 주제, 본문 틀, 보드 미작업). OZ 는 .github/ISSUE_TEMPLATE/topic.yml
node tools/board/board.mjs status <#> "사용자 대기"        # 미작업 | 작업 중 | 사용자 대기 | 작업 완료
node tools/board/board.mjs after <#> <선행#>               # <#> 는 <선행#> 가 닫혀야 시작 (GitHub 이슈 의존 Blocked by)
node tools/board/board.mjs sync                           # 보드에 없는 주제 올리기, 닫힌 것 작업 완료, 목록 찍기 (열린 선행은 "선행: #N")
```

- 세션 시작 sync 목록은 SessionStart 훅이 넣어 준다. `사용자 대기` 주제는 첫 보고에 그대로 알린다. 미작업 주제는 사용자가 맡길 때만 시작한다. 옛 방식 이슈(라벨 `작업`·`요청`, 2026-11-08 전)도 닫힐 때까지 목록에 나온다. 새로 열지 않는다
- 선행: 다른 주제의 결과가 먼저 필요하면 `after` 로 주제끼리만 의존을 건다(주제 안의 순서는 흐름이 맡는다). 선행이 열린 주제를 맡으면 먼저 알린다
- 사용자가 결과를 보내면(체크·댓글·채팅) 그 단계를 체크하고 결과를 한마디 붙인 뒤 `작업 중` 으로 돌린다
- 라벨: Unity 에디터(CLI 연결)가 필요한 주제는 `에디터 필요`, 사용자 몫이 아닌 막힘은 `막힘` + 이유 댓글
- 이슈 도구가 안 되면(gh 로그인 없음) 사용자에게 알리고 채팅으로 보고한다. 클라우드 세션은 GitHub MCP 로 같은 모양을 손으로 연다(라벨 `주제`). 다음 로컬 세션의 sync 가 보드에 올린다
- 보드 보기는 웹에서만 만든다(API 로는 못 만든다). 권장: "전체"(보드, Status 열), "사용자 대기"(거르기 `status:"사용자 대기"`)

## 3. 커밋·브랜치·닫기

- 주제 일을 시작하면(첫 커밋 전이라도) 바로 `git push -u origin HEAD` 하고 `## 관련` 에 `- 브랜치: [<이름>](<저장소>/tree/<이름>) (<날짜>)` 한 줄. 세션마다 한 줄씩 쌓고 끝난 줄도 지우지 않는다. 새 커밋이 생기면 그때마다 push
- 단계를 끝내면 체크하고 그 줄에 커밋 해시, 댓글에 `확인: 어떻게 확인했는지`. 코드 커밋 메시지엔 주제 `#번호`. 할 일·상태만 바꾸는 커밋은 만들지 않는다. 못 하거나 미루는 단계는 체크하지 않고 이유를 댓글로
- 닫기·merge·보고 전에 흐름을 `요청` 원문과 한 줄씩 대조한다. 보고엔 체크 안 된 단계를 주제별로 빠짐없이 적는다. 흐름이 다 끝나고 사용자 확인까지 받으면 닫는다(남은 단계는 다른 주제로 옮겨 링크한 뒤에만)
- 하지 않는 것: 작은 태스크 이슈, 하위 이슈, 담당·종류 칸, 우선순위·기한·추정 칸, 스프린트, Obsidian 칸반(워크트리마다 merge 충돌, 클라우드에서 못 봄)

## 4. 검증 위임 (사용자 결정 2026-11-08, 2026-11-09 고침)

- "문제없이 돌아가는가"(뜨는가·눌리는가·규칙대로 숫자가 바뀌는가·에러 없는가)는 에이전트가 에디터를 켜고 verify-unity 로 직접 확인한다. 통과한 항목은 `## 확인` 에서 체크하고 `(에이전트)` 를 붙인다
- "퀄리티 판단"(보기 좋은가·연출 느낌·어색함·번역 자연스러움)은 사용자 몫. 직접 플레이하는 퀄리티 확인은 에이전트가 하지 않는다. `## 확인` 에 체크리스트(항목마다 할 일·기대 결과 한 줄·`- [ ]`)를 쓰고 `사용자: 확인` 단계를 두고 `사용자 대기`
- 결과가 오면 단계를 체크하고, 실패 항목은 다음 `구현:` 단계로 고친 뒤 그 항목만 담은 `사용자: 다시 확인` 을 둔다. 결과 전에는 "확인됨" 으로 보고하지 않는다
- 에이전트가 돌리는 것은 클릭 없는 자동 검사뿐: 컴파일, EditMode·PlayMode 시험, `tools/ui-audit/sweep.sh`, 스크린샷. 스크린샷은 `verify-artifacts/` 에 두고(저장소 X) 경로를 주제 이슈 댓글에 적는다
