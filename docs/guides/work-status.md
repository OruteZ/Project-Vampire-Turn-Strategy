# 작업 현황 (요청 이슈 + 태스크 + 보드)

> 사용자 결정 2026-11-08 (#49): "미작업 -> 작업 중 -> 작업 완료 이런 플로우로 가고 각 작업에 담당자가 에이전트 또는 사람으로 지정되면 좋겠어. 검증하는 하나의 태스크도 따로 보드를 나누고, 이렇게 이슈하나에 대응되는 태스크가 여러개면 좋겠는데"

## 1. 구조

```
요청 이슈   "요청: UI 대개편 - 스테이지 선택"   라벨 요청       ← OZ 가 요청 폼으로 연 것, 또는 채팅으로 맡긴 일
 ├─ 태스크  "2. 3 레이어 구현"       라벨 작업   담당 에이전트  종류 구현
 ├─ 태스크  "2-b. 원정 지도 1차"     라벨 작업   담당 에이전트  종류 구현
 ├─ 태스크  "장 선택 확인"           라벨 작업   담당 OZ        종류 검증
 └─ 태스크  "잠긴 병종 탭 결정"      라벨 작업   담당 OZ        종류 결정
```

1. **요청 이슈**: OZ 가 New issue → **요청** 폼(`.github/ISSUE_TEMPLATE/request.yml`: 개요, 요구사항, 완료 기준, 참고)으로 연다. 라벨 `요청` 이 저절로 붙는다. 채팅으로 맡긴 일이면 에이전트가 원문을 인용해 같은 모양으로 연다. 에이전트는 OZ 가 쓴 본문을 고치지 않고, 해석·진행은 댓글과 태스크에 쓴다. 작업 기록은 태스크에 쌓는다. 태스크가 모두 닫히면 닫는다 (GitHub 가 하위 이슈 진행률을 보인다).
2. **태스크**: 요청 이슈의 GitHub 하위 이슈. 한 담당이 한 번에 끝낼 수 있는 크기.
3. OZ = 사용자 (GitHub 계정 OruteZ). 에이전트도 같은 계정으로 일해서 GitHub 담당자(assignee)로는 갈리지 않는다. 그래서 담당은 보드 칸으로 둔다.

## 2. 태스크 만들기

```bash
node tools/board/board.mjs task <요청#> <에이전트|OZ> <종류> "<제목>" ["<본문>"]
```

- 이슈를 열고(라벨 `작업`), 본문 첫 줄에 `담당: … · 종류: …`, 둘째 줄에 `요청: #N` 을 쓰고, 요청 이슈의 하위 이슈로 잇고, 보드에 올려 칸(상태 미작업, 담당, 종류)을 채운다.
- 요청 파일에서 온 요청이면 제목 앞에 요구사항 번호를 둔다.
- 클라우드 세션처럼 이 도구가 없으면 같은 모양으로 손으로 연다 (본문 첫 줄을 꼭 쓴다). 다음 로컬 세션의 sync 가 보드 칸을 그 줄로 채운다.

## 3. 보드 칸 (GitHub Project "Vampire Spawn 작업")

| 칸 | 값 | 누가 바꾸나 |
|---|---|---|
| Status | 미작업 → 작업 중 → 작업 완료 | 그 태스크 담당. 태스크를 시작하면 `node tools/board/board.mjs status <#> "작업 중"`. 이슈를 닫으면 `작업 완료` (Project 자동화, 그리고 sync) |
| 담당 | 에이전트 / OZ | 태스크를 만들 때 |
| 종류 | 기획 / 구현 / 검증 / 결정 / 준비 | 태스크를 만들 때 |

- 막힘은 상태가 아니라 라벨 `막힘` 이다. 막힌 태스크는 `작업 중` 에 두고 이유를 댓글로 단다.
- 에디터(Unity CLI 연결)가 있어야 하는 태스크는 라벨 `에디터 필요`.
- OZ 담당 태스크를 OZ 가 끝내고 채팅으로 알리면, 에이전트가 결과를 댓글로 남기고 닫는다.
- 보드: https://github.com/users/OruteZ/projects/5 . 부모(요청 이슈)를 보드에 넣으면 하위 이슈가 저절로 따라 올라간다.
- `gh project item-list --format json` 은 한글 칸 이름(담당·종류)을 깨뜨려 보인다. 칸 값을 볼 때는 `board.mjs sync` 목록이나 웹 보드를 본다.
- 이 방식 전에 연 `작업:` 이슈(#16 #37 #45~#48)는 부모 없이 태스크로 둔다. 본문 첫 줄에 담당·종류를 더했다.

보기 (OZ 가 웹에서 만든다. API 로는 못 만든다):

| 보기 | 모양 | 거르기 | 열 / 가로줄 |
|---|---|---|---|
| 전체 | 보드 | 없음 | Status / 없음 |
| TODO (OZ 할 일) | 보드 | `담당:OZ` | Status / 종류 (검증 태스크가 자기 줄에 따로 모인다) |
| AGENT (에이전트 할 일) | 보드 | `담당:에이전트` | Status / 종류 |
| REQUEST (요청) | 표 | `label:요청` | |

## 4. 태스크 종류

| 종류 | 담당 | 예 | 본문에 쓸 것 |
|---|---|---|---|
| 기획 | 에이전트 | 기획서 쓰기·고치기 | 쓸 문서 |
| 구현 | 에이전트 | 코드·씬·에셋·도구 | 완료 기준, 자동 검사(컴파일·시험·sweep·스크린샷) |
| 검증 | OZ | 화면 전환·키·연출 확인 (CLAUDE.md "검증 위임") | `## 확인` 절: 시작 상태, 항목마다 할 일·기대 결과·`- [ ]`, 에이전트가 이미 돌린 자동 검사 |
| 결정 | OZ | 방향이 갈리는 것, `확정 후보` 를 docs/design 으로 옮기기 | 고를 것, 추천 한 줄 |
| 준비 | OZ | 유료 에셋 내려받기, `gh auth`, API 키, docs/design 에 방향 쓰기, 허락 | 명령이나 순서 |

- 인터랙션이 있는 구현 태스크에는 검증 태스크를 붙인다. 검증에서 실패한 항목은 새 구현 태스크가 되고, 고친 뒤 고친 항목만 담은 검증 태스크를 다시 연다.

## 5. 세션 시작

`node tools/board/board.mjs sync` 를 돈다: `작업`·`요청` 이슈 중 보드에 없는 것을 올리고, 비어 있는 담당·종류를 본문 첫 줄로 채우고, 닫힌 것은 `작업 완료` 로 맞춘다. 몇 번 돌려도 결과가 같다. 끝에 열린 태스크를 담당별로, 그리고 태스크가 아직 없는 새 요청과 태스크가 다 닫힌 요청을 찍는다:

```
에이전트 할 일 2개
  작업 중 #51 도구: tools/board/board.mjs …
OZ 할 일 1개
  미작업  #52 gh 에 프로젝트 권한 주기
새 요청 1개 (태스크 없음, 맡기면 시작): #80 요청: …
```

- 이 목록의 OZ 할 일과 새 요청은 세션 시작 보고에 그대로 적는다. 새 요청은 OZ 가 맡기면 시작한다.
- 보드가 없거나 `gh` 에 project 권한이 없으면 이슈 본문 첫 줄로만 목록을 찍는다 (상태는 "상태 모름").

## 6. 채팅으로 맡긴 요청 이슈 본문

```markdown
채팅으로 맡긴 일.

> 사용자 원문 인용
> 작업 중에 더 온 요청·질문도 받는 즉시 인용

태스크는 이 이슈의 하위 이슈다.

## 관련
- 안내서: docs/areas/<분야>.md
- 기획: docs/design/<파일>
```

- 커밋 메시지에는 태스크 `#번호` 를 적는다.
- 태스크를 닫을 때 댓글: 결과(문서·커밋)와 `확인: 어떻게 확인했는지`.

## 7. 하지 않는 것

- 우선순위·기한·추정 칸, 스프린트. 열린 태스크가 20개를 넘거나 순서를 정하고 싶어지면 우선순위 칸을 더한다.
- Obsidian 칸반. 보드가 md 파일 하나라 워크트리마다 일하는 에이전트끼리 merge 충돌이 나고, 클라우드 세션은 볼 수 없다.
