# 작업 현황 (주제 이슈 + 보드)

> 사용자 결정 2026-11-08: "이슈가 너무 작은 단위의 일들을 담고 있어서, 전체적으로 어떤 태스크들이 흐름으로 돌아가는지 추적되지 않고 휩쓸리는 느낌이야. status에 "샤용자 대기"를 달고 담당자 라벨을 때는 쪽이 ㅎ훨씬 좋을 것 같아. 또한 각각의 이슈가 훨씬더 큰 작업의 단위를 가지면 좋겠어. 핵심 주제를 중심으로 어떻게 돌아가는지 일렬로 보이도록"

## 1. 구조

이슈 하나 = **주제** 하나 (라벨 `주제`). 주제는 기능·화면·도구처럼 여러 번의 기획·구현·확인을 거치는 큰 흐름이다 (예: "장 선택 화면", "다국어", "작업 보드"). 하위 이슈·담당·종류는 없다. 한 주제의 일은 모두 그 이슈 본문의 `## 흐름` 에 순서대로 쌓인다.

```markdown
## 목표
장 선택 화면을 원정 지도 위 3 레이어로 만든다.

## 요청
> (사용자 원문 인용. 채팅으로 맡긴 일이면 에이전트가, 작업 중에 더 온 요청도 받는 즉시 여기 더한다)

## 흐름
- [x] 기획: docs/ui/stage-select.md (a1b2c3d)
- [x] 구현: L1·L2·L3 (d4e5f6a)
- [x] 사용자: 움직임·그늘 확인 → 3·6 이 어색함
- [x] 구현: 칸 감속 (1cdf593)
- [ ] 사용자: 다시 확인 (아래 확인)
- [ ] 구현: 원정 지도 소품

## 확인
(사용자 대기일 때만. 항목마다 할 일·기대 결과·`- [ ]`)

## 관련
- 안내서: docs/areas/<분야>.md
- 기획: docs/design/<파일>
- 브랜치: [claude/stage-select-1a2b3c](https://github.com/OruteZ/Project-Vampire-Turn-Strategy/tree/claude/stage-select-1a2b3c) (2026-11-08)
```

- `## 흐름` 한 줄 = 한 단계. 앞에 `기획:` `구현:` `사용자:` 를 붙인다. 사용자 몫(확인·결정·준비·허락)은 `사용자:` 단계다. 끝나면 체크하고 커밋 해시나 결과를 한마디 붙인다.
- 단계가 일렬로 보이는 것이 핵심이다. 새 일이 오면 그 주제의 흐름 끝(또는 알맞은 자리)에 단계를 더한다. 확인에서 나온 고칠 것도 새 이슈가 아니라 다음 단계다.
- 에이전트는 사용자가 쓴 `목표`·`요청` 문장을 고치지 않는다. `흐름`·`확인`·`관련` 은 에이전트가 고친다.
- 세부 기록(무엇을 어떻게 확인했나, 스크린샷 경로)은 댓글에 쓴다.
- 주제 하나 = 세션 하나로 처리하는 분량이다. 한 세션이 그 주제의 흐름을 처음부터 닫을 때까지 맡고, `사용자:` 단계를 기다린 뒤에도 같은 세션에서 이어 간다. 세션 하나로 끝까지 들고 가기 어려울 만큼 커지면 사용자에게 나눌지 묻는다.
- 어느 주제에도 안 맞는 일이 오면 새 주제를 연다. 한두 단계로 끝날 일이라면 가장 가까운 주제에 넣는다.

## 2. 상태 (GitHub Project "Vampire Spawn 작업" 의 Status)

| 상태 | 뜻 | 누가 바꾸나 |
|---|---|---|
| 미작업 | 열렸지만 아직 아무도 손대지 않음 | 연 때 |
| 작업 중 | 에이전트가 다음 단계를 하고 있음 | 에이전트, 시작할 때 |
| 사용자 대기 | 다음 단계가 `사용자:` 단계. 무엇을 해 달라는지는 `## 확인` 이나 댓글에 | 에이전트, 사용자 단계에 이르렀을 때 |
| 작업 완료 | 이슈를 닫음 | 닫으면 저절로 (Project 자동화, sync) |

```bash
node tools/board/board.mjs open "<제목>" ["<목표>"]       # 주제 이슈 열기 (라벨 주제, 본문 틀, 보드 미작업)
node tools/board/board.mjs status <#> "사용자 대기"        # 미작업 | 작업 중 | 사용자 대기 | 작업 완료
node tools/board/board.mjs sync                           # 보드에 없는 주제 올리기, 닫힌 것 작업 완료, 목록 찍기
```

- 사용자가 결과를 보내면(체크·댓글·채팅) 에이전트가 그 단계를 체크하고 결과를 한마디 붙인 뒤 `작업 중` 으로 돌린다.
- 막힘(사용자 몫이 아닌 것)은 라벨 `막힘` 과 댓글. Unity 에디터가 있어야 하는 주제는 라벨 `에디터 필요`.
- 주제의 흐름이 다 끝나고(남은 단계 없음) 사용자 확인까지 받으면 닫는다. 닫기 전에 `요청` 의 원문과 흐름을 한 줄씩 대조한다.
- 보드: https://github.com/users/OruteZ/projects/5 . 보기는 웹에서만 만든다 (API 로는 못 만든다). 권장: "전체"(보드, Status 열), "사용자 대기"(거르기 `status:"사용자 대기"`).
- 클라우드 세션처럼 이 도구가 없으면 같은 모양으로 손으로 연다 (라벨 `주제`). 다음 로컬 세션의 sync 가 보드에 올린다.

## 3. 세션 시작

`node tools/board/board.mjs sync` 를 돈다. 열린 주제를 상태별로, 흐름 진행(체크/전체)과 다음 단계와 함께 찍는다:

```
사용자 대기 1개
  #93 장 선택 화면  [4/6]  다음: 사용자: 다시 확인 (아래 확인)
작업 중 1개
  #94 다국어  [2/5]  다음: 구현: 결과 창 영어
```

- `사용자 대기` 는 세션 시작 보고에 그대로 적는다. 미작업 주제는 사용자가 맡기면 시작한다.
- 옛 방식 이슈(라벨 `작업`·`요청`, 2026-11-08 전)도 닫힐 때까지 같은 목록에 나온다. 새로 열지 않는다.

## 4. 커밋·기록

- 코드 커밋 메시지에 주제 `#번호` 를 적는다.
- 단계를 체크할 때 그 줄에 커밋 해시를, 댓글에 `확인: 어떻게 확인했는지` 를 남긴다.
- **브랜치 연결**: 세션이 주제 일을 시작하면(첫 커밋 전이라도) 작업 브랜치를 원격에 올리고(`git push -u origin HEAD`) 본문 `## 관련` 에 `- 브랜치: [<이름>](<저장소>/tree/<이름>) (<날짜>)` 한 줄을 더한다. 한 주제를 여러 세션이 거치면 세션마다 한 줄씩 쌓고, 끝난 브랜치 줄도 지우지 않는다(어느 세션이 무엇을 했는지 기록). 브랜치에 새 커밋이 생기면 그때마다 `git push` 한다

## 5. 하지 않는 것

- 작은 태스크 이슈, 하위 이슈, 담당·종류 칸, 선행 관계. 흐름 순서가 곧 선행이다.
- 우선순위·기한·추정 칸, 스프린트.
- Obsidian 칸반. 워크트리마다 merge 충돌이 나고 클라우드 세션은 볼 수 없다.
