# 요청 파일 (docs/request)

사용자가 원하는 일을 파일로 남기는 곳이다. 채팅으로 맡긴 일과 같은 무게로 다룬다. 작업 기록은 GitHub 이슈가 맡고, 요청 파일은 사용자 원문과 진행 상태를 보여 준다.

## 사용자가 하는 일

1. `docs/request/_TEMPLATE.md` 를 복사해 `NNN_<짧은영문이름>.md` 로 둔다. 번호는 다음 번호, 세 자리.
2. 머리말의 `id`, `created` 를 채우고 `status: request` 로 둔다. 본문(개요, 요구사항)을 쓴다.
3. 채팅에서 "리퀘스트 처리" 또는 "N번 리퀘스트 처리" 라고 맡긴다.

## 에이전트가 하는 일

1. **세션 시작.** `node tools/requests/check.mjs` 로 요청 목록을 본다. 새 요청(`status: request`)이나 상태가 어긋난 요청이 있으면 사용자에게 알린다. 요청 파일만 보고 일을 시작하지 않는다. 사용자가 채팅으로 맡기면 시작한다.
2. **받기.** 요청 하나 = 요청 이슈 하나(`요청: <제목>`, 라벨 `요청`, docs/guides/work-status.md).
   - 요청 이슈 본문 맨 위에 요청 파일 경로와 개요를 인용한다.
   - 요구사항 번호마다 태스크(하위 이슈)를 하나 이상 연다. 제목 앞에 같은 번호, 담당(`에이전트` / `OZ`)과 종류를 정한다: `node tools/board/board.mjs task <요청#> <담당> <종류> "<번호>. <제목>"`.
   - 요청 머리말에는 `status: working`, `issue: #<요청 이슈 번호>` 를 적는다.
3. **애매하면.** CLAUDE.md "기획 구체화" 를 따른다. 정한 해석은 이슈 댓글과 그 분야 안내서 결정 표(`출처: docs/request/<파일>`)에 남긴다.
4. **막히면.** 막힌 태스크에 라벨 `막힘` 과 이유 댓글. 요청 전체가 막혔으면 요청 이슈에도 `막힘` 을 붙이고 요청 머리말을 `status: blocked` 로 바꾼다.
5. **끝.** 태스크 목록을 요청 요구사항과 한 줄씩 대조한다(CLAUDE.md "요청 빠짐 막기"). 태스크가 모두 닫혔으면 결과를 요청 이슈 댓글로 달고 닫은 뒤 요청 머리말을 고친다: `status: done`, `done: <끝난 날짜 YYYYMMDD>` (커밋은 이슈에 적는다). 다 못 했으면 `done` 으로 두지 않는다.
6. **커밋.** 요청 파일은 코드 커밋에 같이 넣는다. 머리말만 바꾸는 커밋은 따로 만들지 않는다(CLAUDE.md "할 일·상태만 바꾸는 커밋은 만들지 않는다").

## 누가 무엇을 고치나

| 부분 | 사용자 | 에이전트 |
|---|---|---|
| 본문(제목, 개요, 요구사항, 완료 기준, 참고) | 쓴다 | 고치지 않는다 |
| 머리말 `id`, `created` | 쓴다 | 비었으면 채운다 |
| 머리말 `status`, `issue`, `done` | 바꿔도 된다(예: 취소는 `status: dropped`) | 위 순서대로 바꾼다 |
| 파일 이름 | 정한다 | 바꾸지 않는다 |

상태: `request`(새 요청) → `working`(이슈 진행 중) → `done`. 막히면 `blocked`, 사용자가 접으면 `dropped`.

## 다른 문서와 겹치는 곳

| 문서 | 무엇 | 요청과의 관계 |
|---|---|---|
| `docs/request/` | 사용자가 원하는 일(작업 요청) | 원문. 본문은 사용자만 쓴다 |
| GitHub 요청 이슈 + 태스크(하위 이슈), 보드 | 작업 기록, 담당·상태, 결과 | 요청 하나당 요청 이슈 하나, 태스크 여럿. 진행 상황의 원본은 이슈와 보드다 (docs/guides/work-status.md) |
| `docs/design/` | 사람이 쓰는 기획 방향 | 요청이 게임 기획(규칙·수치·화면)을 바꾸려 하면 요청만으로 구현하지 않는다. docs/design 에 방향이 있으면 기획 에이전트가 기획서를 고친 뒤 구현하고, 없으면 사용자에게 docs/design 에 방향을 적을지 묻는다 |
| 기획서 (`docs/systems`, `docs/content`, `docs/ui`, `docs/art`) | 기획 에이전트가 쓰는 구현 요구사항 | 게임 기능 요청은 기획서를 거쳐 구현한다. 도구·작업 방식 요청(편집기, 파이프라인)은 기획서 없이 바로 구현한다 |
| `docs/areas/` | 분야별 경로, 지금 유효한 결정 | 요청에서 나온 결정은 그 분야 결정 표에 `시험 중` 으로 남긴다 |
| `docs/dev/` | 구현 기록 | 요청으로 만든 코드 구조는 여기 적는다 |
| `docs/guides/` | 작업 규칙, 사용법 | 요청이 새 도구나 사용법을 만들면 여기 적는다 |

채팅으로 맡긴 일은 지금처럼 이슈에 원문을 인용한다. 같은 일을 요청 파일로도 쓰면 이슈에 두 출처를 함께 적는다.
